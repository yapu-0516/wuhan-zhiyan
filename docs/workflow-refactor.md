# 城市智眼业务闭环重构：第一阶段

本阶段把原先“页面直接操作事件”的结构，扩展成可追溯的业务闭环：

```text
数据资源 → 监测任务 → 运行记录 → 事件 → 研判 →（情景推演）→ 工单 → 复盘
```

现有 `/api/events`、AI 分析任务和情景推演接口保持兼容。业务任务、运行、研判、工单和复盘采用独立对象；
数据资产在原目录结构上增量补充空间、时相、质量和版本画像，旧数据库通过补列与回填迁移，不删除已有记录。

## 数据对象

| 对象 | 编号 | 职责 |
| --- | --- | --- |
| `MonitoringTask` | `MT0001` | 业务监测目标、区域、数据源、规则、责任人和周期 |
| `MonitoringRun` | `MR0001` | 一次业务运行，关联 AI 作业和其产出的事件 |
| `Event` | `E0001` | 统一风险对象，保持现有状态机和页面兼容 |
| `AssessmentRecord` | `AS0001` | 事件候选、核查、确认或误报的研判证据 |
| `WorkOrder` | `WO0001` | 核查、处置、复测等具体执行工作 |
| `ReviewRecord` | `RV0001` | 任务、事件或演练的复盘结论 |

关键边界：

- 业务任务 `MonitoringTask` 与 AI 分析作业 `Task` 分开。
- 事件状态与工单状态分开；一个事件可以包含多个工单。
- 研判记录保留每一轮结论，不覆盖历史判断。
- 复盘记录引用任务、事件或演练，不重复存储完整业务过程。
- 情景运行可写入工单的 `scenario_run_id`，作为选定方案的来源引用。
- 数据资源只有在 `analysis_status=ready` 时表示已完成基本校验；目录中存在资源点不等于资源实时可调度。

## API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET/POST | `/api/monitoring-tasks` | 查询、创建业务监测任务 |
| GET/PATCH | `/api/monitoring-tasks/{id}` | 详情、状态与规则更新 |
| POST | `/api/monitoring-tasks/{id}/execute` | 立即运行真实算法并建立运行记录 |
| GET/POST | `/api/monitoring-runs` | 查询、登记业务运行 |
| GET/POST | `/api/assessments` | 按事件查询、创建研判记录 |
| GET/POST | `/api/work-orders` | 查询、创建工单 |
| POST | `/api/scenario-runs/{id}/dispatch` | 将用户确认的推演方案转为协同处置工单 |
| GET/PATCH | `/api/work-orders/{id}` | 工单详情和执行流转 |
| POST | `/api/work-orders/{id}/feedback` | 提交现场文字、定位和最多 5 张照片 |
| GET/POST | `/api/reviews` | 查询、创建复盘记录 |

周期任务使用 `rule_config.interval_minutes` 保存频率，`next_run_at` 保存下次执行时间。
后端调度器只执行 `schedule_type=periodic`、`status=scheduled` 且已到期、尚未超过 `end_at` 的任务。
算法完成后周期任务回到 `scheduled` 并写入下一次时间；失败时任务和运行记录均保留失败原因。

`monitoring_task_templates` 保存可复用任务模板，前端可从模板带入区域、风险类型、数据资源、
周期、责任人和通知对象，也可将现有任务另存为模板。模板不是运行中的 AI 任务。
任务模板可在页面编辑、删除并查看规则修订历史；规则变更写入 `task_template_revisions`。
任务表单同时支持开始/结束时间、按场景设置触发阈值和通知对象；配置写入任务记录，
运行记录继续保存覆盖范围和算法质量。
规则 JSON 还支持 `conditions` 多指标条件、`min_consecutive` 连续命中次数和
`cooldown_minutes` 冷却时间；条件不满足时不生成事件，但仍保留运行记录。
`rule_config.algorithm_params` 会作为关键字参数传给所选分析器，例如内涝预测时长
`{"forecast_min": 30}`；对应的算法名称和版本仍记录在运行结果中。

## 状态机

监测任务：

```text
draft → scheduled → running → completed
                 ↘ failed → scheduled/running
```

工单：

```text
pending → accepted → in_progress → completed → verified
                                  ↘ rejected → in_progress
pending/accepted/in_progress → cancelled
```

事件状态仍使用现有 `pending → monitoring/processing → resolved` 状态机。
工单已完成不等于事件已办结，事件仍需经过复核后独立办结。

## 内涝示例闭环

种子数据建立一条完整记录链：

`MT0001 → MR0001 → 已办结内涝事件 → AS0001 → WO0001/WO0002 → RV0001`

它用于验证任务、数据来源、算法指标、研判证据、现场反馈和复盘之间均可追踪。

情景推演生成常规、不利和提前干预三套结果。用户选择一套方案并确认关联事件后，
系统按场景动作模板生成多张工单；工单保留 `scenario_run_id`，在协同处置中继续接单、执行和复核。
情景可以从现有事件详情直接创建，自动带入事件位置、时间、可用资源数量和来源事件编号；
演示模型输出会补充受影响建筑与道路编号，并支持导出完整 JSON 结果。
情景模板保存场景类型与完整参数，可从模板建立会话并直接运行，不需要重新输入整段假设。
情景模板支持编辑、删除与参数修订历史；每次编辑都生成不可变版本，已运行结果继续引用原版本。
情景还可从应急资源库存选择具体资源形成预留，修改选择时释放旧预留并重新占用。

现场反馈保存为工单 `feedback` 时间线中的 `field_feedback` 记录，包含操作人、时间、定位、文字和照片地址。
工单响应中的 `sla` 由状态流转时间计算接单响应、执行耗时、复核耗时、已用时间、剩余时限和超时状态；
超时工单与事件办结状态分别判断。

协同处置前端支持转派、资源使用记录和复测 / 复飞申请；转派与资源使用继续写入工单反馈时间线，
复测 / 复飞创建新的工单，不覆盖原工单结果。
资源使用从 `emergency_resources` 库存选择并扣减可用数量，避免工单填写与资源台账脱节。
现场文字或照片反馈可一键转入风险研判，生成 `needs_review` 研判记录并保留原工单反馈证据。

研判工作区按事件点查询 300 m 内建筑、道路和敏感设施，查询结果只作为当前影响的辅助证据，
不替代现场核查。页面同时列出同类型、1 km 内且两小时内的相近告警，允许在形成研判时关联到证据链。
相近告警也可执行正式合并：主事件保留 `merged_event_ids`，被合并事件留存 `merged_into` 并办结，
双方事件日志保留合并原因。
复盘工作区可自动读取任务、事件日志、研判、工单、情景结果和 SLA，
生成可编辑的复盘摘要、指标、发现、建议与时间线。
确认后的复盘进入案例库并可导出 Markdown 报告；审核后的规则配置可应用到任务模板，
每次应用生成独立修订版本并保留来源复盘编号。

## 数据资源画像

每条数据资产记录以下信息：

- `spatial_extent`：空间范围名称与 WGS84 边界；
- `time_start` / `time_end`：覆盖时相，实时流可只保留起点；
- `crs`：坐标参考系；
- `quality_score` / `quality_notes`：质量检查得分与已知限制；
- `version`：数据版本；
- `analysis_status`：`ready | pending | unavailable | unknown`。

上传文件默认标记为 `pending`，待完成坐标、时相和字段校验后才能作为分析输入。
校验记录保存在 `data_validations`：通过要求坐标、时相和字段三项全部有效，资源才更新为 `ready`；
任务创建和执行都会拒绝未通过校验或已失效的 `Dxxxx` 数据资源。
数据目录接口和页面支持按类型、状态、关键词、时相范围及“中心点 + 半径”检索；
数据详情可通过空间范围中心直接跳转到三维总览定位。
自动预检会检查本地文件、时空登记、CSV 字段和时间列、经纬度列与重复记录；
预检结果只作为人工校验依据，不会直接放行数据。

## 公共支撑

- `operator_accounts`：6 个演示身份，覆盖值班、研判、调度、现场、数据维护和系统管理角色；
- `responsibility_grids`：按行政区组织责任单位、责任人、联系方式和风险类型，并支持系统管理页维护；
- `emergency_resources`：把医院、消防站、派出所、学校的空间点位与容量、可用数量和调度状态分开记录；
- `notifications`：工单创建、状态变化、现场反馈和复盘确认生成站内提醒；
- `audit_logs`：统一记录非只读 API 的方法、路径、演示身份、关联对象、响应状态和修改前后值；
- SLA 汇总读取工单状态流转时间，输出活跃、超时、平均响应、平均执行、平均复核以及按业务日趋势。
- 系统管理展示数据库类型、模拟器开关、周期任务扫描间隔、任务/运行/数据状态和算法版本。
- 本地运行配置可调整分析阶段节奏、周期任务扫描间隔和单文件上传上限；配置仅作用于当前进程，
  不依赖外部配置中心。
- 建筑与道路可按对象编号在系统管理中修改属性和 GeoJSON 几何，保存后重建空间索引与实时路况对象。
- 业务关系图把数据资源、任务、运行、分析作业、事件、研判、推演、工单和复盘统一成节点与关系，
  支持按任一对象定位双向链路，并导出完整 JSON。

当前通过 `X-Operator-Id` 演示身份署名，不表示已经实现正式认证、组织同步或权限拦截。
城市总览按责任网格过滤事件，并在业务运行摘要中显示可分析数据资源和最近数据更新时间。

## 迁移与回滚

- 新表通过 SQLAlchemy `create_all` 增量创建。
- 旧 `data_assets` 表自动补充画像字段并回填保守默认值；旧 `audit_logs` 自动补充修改前后值字段，
  不重建数据库、不删除用户上传记录或历史审计。
- 现有 API 和前端无需改动，继续使用原事件接口。
- 演示数据通过 `POST /api/demo/reset` 重新生成，并包含一条内涝闭环。
- 回滚新增列时应先在副本数据库验证；不建议直接删列，以免破坏已登记的数据资源画像。
- 当前服务使用 SQLite；若迁移 PostgreSQL/MySQL，应先在该实际数据库版本上验证建表和 JSON 字段行为。
